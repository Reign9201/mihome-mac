# 摄像头实时查看

结论：核心诉求可做，但它和开关控制不是同一条链路。`mijia-api` 与 `MiHome-Windows` 都没有视频能力；第一版需要引入一个本机取流助手，App 负责登录、设备列表、画面窗口和交互。远程查看不在第一版范围内，Mac 不在家时需要用户已有的家庭 VPN，App 不内置公网穿透。

## 一、范围

### 1.1 第一版做

- 总览页的 3 路监控缩略图，点击进入对应摄像头。
- 单画面实时查看，显示分辨率、编码、码率、连接路径和延迟。
- 最多 4 路宫格（原型为 3 路），默认使用子码流，双击或点击切到单画面。
- 支持机型的云台四向控制与回中。
- 支持机型的双向语音，按住说话。
- 截图、手动录制到本机、全屏、隐私遮蔽。
- 本机录制片段列表与手动截图入口。

### 1.2 第一版不做

- 小米云存储录像回放。它依赖小米云服务，接口不在两个开源仓库里。
- 摄像头固件升级、参数设置页、OSD 与夜视调节。
- 公网穿透。没有 VPN 时，Mac 不在家就看不了，界面必须直说。
- 跨品牌 ONVIF。第一版只处理小米生态的 CS2/TUTK 机型。

### 1.3 支持条件

一台摄像头要出现在监控页，需要同时满足：

1. 机型在 go2rtc 的 `xiaomi/mess` 或 `xiaomi/legacy` 支持列表里。
2. 摄像头与 Mac 在同一局域网，UDP 可直达；跨网段、隔离 AP、访客网络都不行。
3. 登录账号对这个摄像头有查看权限。
4. 首次连接时能访问小米云取 P2P 密钥；之后短时间断网仍可重连。

不满足条件的摄像头仍然出现在“全部设备”，但不显示“查看”按钮，避免点了才发现不支持。

## 二、为什么两个仓库帮不上

`mijia-api` 的代码只处理 HTTP 设备接口、属性、场景和统计，没有 RTP、HLS、P2P、解码相关实现。`MiHome-Windows` 把摄像头当作“没有开关能力”的设备：它能显示在线状态，能出现在托盘，但没有视频窗口。

米家摄像头的实时流也不走普通 MIoT 属性。部分机型的 MIoT 规格有 `start-rtsp-stream`、`start-hls-stream`、`start-p2p-stream` 动作，但成功率和返回格式随机型、固件、账号权限变化，不能当成通用 RTSP 地址。直接照搬 `mijia-api` 的 `prop/get` 拿不到画面。

## 三、取流链路

```
扫码登录（sid=xiaomiio）
        │
        ├── passToken、userID、ssecurity
        │
        ▼
App 写入 Keychain，启动 go2rtc helper
        │
        ▼
go2rtc 用 userId + passToken 登录小米云
        │
        ├── 取 P2P 密钥、vendor、P2P 参数
        ▼
go2rtc 与摄像头建立 CS2 / TUTK 连接
        │
        ├── HLS / MP4 / RTSP / WebRTC 输出
        ▼
App：AVPlayer 播 HLS，或 WKWebView 播 WebRTC
```

### 3.1 登录复用

项目已经能扫码拿到 `passToken`。go2rtc 的 `LoginWithToken(userID, passToken)` 正好使用这两个值，通过 Cookie 请求 `account.xiaomi.com/pass/serviceLogin` 换 `ssecurity`。因此用户不需要再输入小米密码，也不需要二次短信验证。

App 只把 `userID` 和 `passToken` 交给本机 helper，不写配置文件到用户目录，不写日志。helper 退出时凭据随进程内存消失。

### 3.2 helper 进程

- 二进制随 App 打包，`Contents/Resources/go2rtc`，启动时校验签名与 SHA-256。
- 监听 `127.0.0.1` 的随机端口，不用默认 1984 暴露给局域网。
- App 启动时拉起，空闲 10 分钟且没有画面时退出；有画面时保持。
- 退出 App、切换账号、系统睡眠前发送停止信号，超时后强制结束。
- 崩溃后最多重启 3 次，仍失败则监控页显示“取流服务不可用”，不影响开关控制。

### 3.3 播放

| 方式 | 延迟 | 适用 | 取舍 |
|---|---|---|---|
| HLS | 2–5 秒 | 单画面、宫格 | AVPlayer 原生支持，硬解稳定，延迟高 |
| MP4 | 1–3 秒 | 单画面 | 需要处理分片，A/V 同步要自己做 |
| WebRTC | 300–800 毫秒 | 单画面、对讲 | 需要 WKWebView 或原生 WebRTC，复杂度高 |

第一版用 HLS 保证稳定，双击画面或点“低延迟”再切 WebRTC。宫格只开 HLS 子码流，不同时开 4 路 WebRTC。

### 3.4 不直接走 MIoT

MIoT 的摄像头服务是“控制面”，不是“媒体面”。`start-rtsp-stream` 返回的是开流结果或地址，实际媒体流仍要走 P2P。把控制面当媒体面，会在不同机型上得到完全不同的结果，也无法处理双向语音。

## 四、页面

### 4.1 总览横条

- 3 个 16:9 缩略图，横向等分；窄窗口改为横向滚动。
- 左上角红点表示直播，右上角显示“直播中 / 遮蔽 / 离线”。
- 下方一行：名称、分辨率、连接路径。
- 右侧“打开监控台”进入完整页面。
- 点缩略图直接进入该摄像头单画面，不经过列表。

### 4.2 单画面

画面区占左侧主要宽度，右侧是 3 路摄像头列表，底部是事件时间线。

画面叠层：

- 左上：LIVE / REPLAY、时钟、分辨率、编码、码率、P2P 延迟。
- 左下：摄像头名、房间、镜头角度、协议。
- 右下：录制状态。
- 右侧中部：云台方向盘，仅 `ptz=true` 时显示。
- 底部工具条：画质、暂停、对讲、录制、回放、全屏、遮蔽。

### 4.3 宫格

- 2×2 最多 4 路，3 路时第三路占满第二行。
- 每格显示名称、LIVE、延迟；当前格有强调边框。
- 默认子码流；点格子切单画面，双击全屏。
- 同一时间只允许一路开声音，避免多路回声。

### 4.4 事件与录制

原型里的事件时间线是演示数据。正式版第一版只承诺两类内容：

1. App 手动录制的片段，存在本机，可在时间线回放。
2. 手动截图，按日期归档。

摄像头自身的移动侦测事件是否可读，取决于机型和云接口，不纳入第一版承诺。界面不把“移动侦测”写成已实现能力，除非对应机型验证通过。

## 五、交互细节

| 操作 | 反馈 |
|---|---|
| 切换摄像头 | 画面淡入，旧流 300 毫秒后关闭，避免同时占两条连接 |
| 切换画质 | 先显示新码率，再重建播放器；不清空当前帧 |
| 云台 | 按下发一次，长按每 200 毫秒发一次，松开停止 |
| 对讲 | 按住说话，松开发送；没有麦克风权限时先弹系统授权 |
| 截图 | 画面闪白 120 毫秒，保存到设置目录，Toast 给路径 |
| 录制 | 按钮变红，状态栏显示已录制时长；再点停止并落盘 |
| 全屏 | 双击画面或按钮，Esc 退出；全屏时隐藏侧栏 |
| 遮蔽 | 有硬件遮蔽的机型发设备指令；没有的机型只做本地遮罩，并明确写“仅本地遮罩” |

## 六、状态与错误

| 状态 | 画面 | 文案 | 操作 |
|---|---|---|---|
| 连接中 | 最后一帧 + 转圈 | 正在建立局域网连接 | 可取消 |
| 直播中 | 实时画面 | 局域网 P2P · 38 ms | 正常控制 |
| 重连中 | 冻结最后一帧 | 连接中断，正在重连（第 2 次） | 立即重试 |
| 离线 | 灰底 + 摄像头图标 | 摄像头离线，最后在线 18:32 | 刷新 |
| 不支持 | 灰底 + 说明 | 该型号暂不支持 Mac 实时查看 | 查看支持列表 |
| 不在同一局域网 | 灰底 + 网络图标 | 需要与摄像头在同一局域网，或先连接家庭 VPN | 打开网络设置 |
| helper 失败 | 灰底 + 警告 | 取流服务未启动 | 重启服务、导出日志 |
| 隐私遮蔽 | 全黑 + 锁图标 | 已开启遮蔽，画面不会离开设备 | 解除 |

重连策略：1 秒、2 秒、4 秒、8 秒，最多 5 次；仍失败进入离线，不无限重试。网络路径变化时立即重试一次。

## 七、性能预算

以下是目标值，不是实测值。

| 指标 | 目标 | 上限 |
|---|---:|---:|
| helper 冷启动到可连接 | 300 ms | 800 ms |
| 局域网首帧（HLS） | 1.5 s | 3 s |
| 局域网首帧（WebRTC） | 500 ms | 1.2 s |
| 单路 1080p 硬解 CPU | 5% | 10% |
| 单路 1080p 额外内存 | 60 MB | 100 MB |
| 4 路 720p 子码流额外内存 | 140 MB | 220 MB |
| 切换摄像头 | 400 ms | 800 ms |
| 截图落盘 | 200 ms | 500 ms |

实现要点：

- 用 VideoToolbox 硬解，不把 YUV 帧搬到 CPU 再转 UIImage。
- 宫格只开子码流，单画面才切主码流。
- 画面不可见时暂停解码，保留最后关键帧。
- 录制用 AVAssetWriter，直接写 H.264 原始帧，不二次转码。
- 带宽估算：1080p 主码流 2–3 Mbps，720p 子码流 0.5–1 Mbps；4 路宫格控制在 4 Mbps 以内。

## 八、安全与隐私

- 摄像头视频只在 Mac 与本机 helper 之间流动，不上传第三方服务器。
- helper 只监听 `127.0.0.1`，端口随机，启动时生成一次性访问令牌。
- `passToken` 只放 Keychain；helper 配置用临时文件，权限 0600，退出即删。
- 日志只记录连接状态、耗时、错误码，不记录 URL 里的 token、不记录画面。
- 截图与录像存本机，默认目录 `~/Movies/MiHome`，设置页可改；不自动上传相册。
- 隐私遮蔽优先调用设备能力；只能本地遮罩时，界面必须写明“仅本地遮罩”，不能宣称镜头已断开。

## 九、机型验证清单

上线前至少完成下面这张表，不能只用一台设备验收。

| 项目 | 验证内容 |
|---|---|
| 型号 | 型号、固件版本、`spec_type` |
| 协议 | CS2 还是 TUTK，UDP 还是 TCP |
| 登录 | 扫码 `passToken` 能否被 go2rtc 接受 |
| 首帧 | 冷启动、热启动、切换摄像头的耗时 |
| 画质 | 主码流、子码流、2K/1080p/720p 实际分辨率 |
| 云台 | 四向、回中、长按连续转动 |
| 对讲 | 是否有回声、延迟、权限提示 |
| 遮蔽 | 是硬件遮蔽还是本地遮罩 |
| 断网 | 拔网线、关 Wi-Fi、睡眠唤醒后的重连 |
| 稳定性 | 连续播放 2 小时的内存与丢帧 |

建议先用用户手上的客厅摄像头做第一台，再补一台不同协议（CS2 与 TUTK 各一台）。没有覆盖到的型号在“全部设备”里降级为状态卡片，不显示监控入口。

## 十、原型对应

`prototype/index.html` 的“监控”页已经实现：

- 3 路摄像头，2 路 CS2、1 路 TUTK。
- 主画面、宫格、画质切换、云台、对讲、录制、截图、全屏、遮蔽。
- 事件时间线、回放模式、摄像头切换。
- 画面由 canvas 绘制，用来验证布局、状态和交互，不接真实视频流。

原型文案中的延迟、码率、分辨率都是演示值；正式版以实测为准。

## 术语说明

**go2rtc**：一个用 Go 写的流媒体网关，能把多种摄像头协议转成 HLS、MP4、RTSP 或 WebRTC。本文用它作为 Mac 本机的取流助手。

**CS2**：小米摄像头使用的一种 P2P 传输协议，常见于较新的机型。

**TUTK**：ThroughTek 的 P2P 协议，小米部分老款摄像头使用。

**P2P**：点对点连接。画面不经过厂商服务器中转，由 Mac 与摄像头直接建立连接。

**HLS**：HTTP Live Streaming，基于 HTTP 的分片视频协议，AVPlayer 原生支持，延迟通常 2–5 秒。

**WebRTC**：浏览器与原生端都支持的实时通信协议，延迟可以做到 1 秒以内。

**VideoToolbox**：Apple 的硬件编解码框架，用 GPU 解码 H.264/H.265。

**passToken**：小米登录后得到的长期凭据，用来换 `serviceToken` 和 `ssecurity`。

**P2P 密钥**：建立摄像头点对点连接前，需要向小米云换取的一次性密钥。

**硬解**：用 GPU 或专用解码单元解码视频，不占满 CPU。
