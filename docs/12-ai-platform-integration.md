# AI 指令与飞书/企业微信/钉钉接入

## 结论

这个项目适合接入 AI 大模型和飞书、企业微信、钉钉，但要把“能演示”与“能让普通用户快速接入”分成两条产品路径：

1. **普通用户主路径：共享官方机器人。** 你部署一个云端多租户网关，所有用户添加同一个官方机器人，发送一次性配对码绑定自己的 MiHome Mac。用户不需要创建飞书/企业微信应用，也不需要公网 IP。
2. **企业/极客路径：自建应用 + 长连接。** 管理员在自己的飞书或企业微信后台创建应用，把 Bot 凭据填入 MiHome Mac。当前桌面端已经支持这条路径，且长连接不需要公网回调。

“每个用户自己创建企业自建应用”不能作为大众首发路径。飞书自建应用默认只服务一个企业，企业微信智能机器人也需要对应企业管理员配置，普通用户既没有权限，也不应该理解回调、Token 和加密参数。

## 已实现能力

- 本地规则优先解析开关、绝对/相对温度、目标湿度、亮度、色温、RGB 颜色、风速、扫风/摇头、音量、静音、窗帘开合、扫地机器人清扫/回充、门锁、播放控制和批量控制等高频指令。
- 支持“打开空调并调至 24°C”“关灯、关空调、打开空气净化器”等组合指令；后续子句会继承前一条的设备、房间和家庭目标。
- 支持“关闭所有灯，除了客厅灯”的排除范围，并同时支持阿拉伯数字、中文数字和常见英文控制词。
- 本地规则未命中时，可调用任意 OpenAI 兼容 `chat/completions` 接口做意图解析。
- 模型只接收家庭、房间、设备名称、能力与值，不接收米家 DID、Cookie、Token。
- 真实 `did/siid/piid` 始终由本机根据设备目录解析，模型不能直接生成设备 ID。
- 执行前校验可写能力，执行后尽量回读状态；门锁、摄像头等高风险操作进入二次确认。
- 平台事件按事件 ID/消息 ID 去重，执行结果写入本地审计文件。
- 飞书支持 Webhook 与事件长连接。
- 飞书长连接采用有上限的指数退避重连；连续失败后停止重试并显示“重新连接”按钮，避免电脑待机或长时间断网时无限重试。
- 接入中心会针对心跳超时、凭据/权限错误、网络或代理失败、连接被新会话替换给出自助诊断；Webhook 模式支持复制完整本机回调地址。
- 飞书订阅“用户进入与机器人的会话”或“机器人进群”事件后，会向对应会话自动发送一次欢迎语和配对引导。
- 电脑从睡眠恢复后会按系统时间差检测唤醒，并统一重建已配置的飞书、企业微信和钉钉长连接；窗口重新获得焦点或检测到网络从断开恢复时，仅重连已断开的平台。
- 企业微信支持智能机器人 API 长连接，包含认证、心跳、指数退避重连和流式回复。
- 钉钉支持企业内部机器人 Stream 长连接，无需公网回调，包含执行前确认和普通文本回复。
- 飞书语音消息会下载音频后在本机转写；企业微信和钉钉优先使用平台返回的语音转写结果。
- 平台用户通过 10 分钟有效、单次使用的 6 位配对码绑定家庭。
- 本地 HTTP 网关只监听 `127.0.0.1`，API 使用 Bearer Token。
- 模型配置页提供真实连接测试，可验证接口地址、模型名和 API Key。

## 本地指令矩阵

本地解析不按设备型号写死，而是把话术映射到设备 MIoT spec 中实际存在的能力。设备没有对应属性或安全动作时，会明确提示不支持，不会猜测写入地址。

| 类别 | 常用说法 | 能力映射 |
|---|---|---|
| 电源 | 打开/关闭、开机/关机、启动/停止、通电/断电 | `on`、`is_on`、`turn_on`、`turn_off` |
| 目标温度 | 调到 26 度、调高一度、降低两度、太热了、有点冷 | `target_temperature` 或升温/降温 action |
| 目标温度扩展 | 热水器调到 60 度、冰箱调到 4 度 | `target_temperature`，实际范围仍按 MIoT spec 校验 |
| 湿度 | 客厅湿度多少、加湿器湿度调到 60%、除湿机设到 50% | `relative_humidity`；只读传感器不会被写入 |
| 亮度 | 亮度 50%、调到 30、最亮、调暗一点、太亮了 | `brightness` 或调亮/调暗 action |
| 色温 | 暖光、冷光、自然光、3500K、色温调暖一点 | `color_temperature` 或色温 action |
| RGB 颜色 | 灯调成蓝色、客厅灯变红、颜色设为 #FF8000 | 设备存在 `color`/`rgb` 可写属性时写入 RGB 数值 |
| 空调模式 | 制冷、制热、暖气、除湿、送风、通风、自动、睡眠 | `mode` / `ir_mode` |
| 风速 | 最大风、最小风、中风、三档、风大一点 | `fan_level`、`mode` 或风速 action |
| 扫风/摇头 | 打开上下扫风、关闭左右摆风、风扇摇头、停止摇头 | `vertical_swing`、`horizontal_swing`、`oscillate`；设备没有对应属性时明确提示 |
| 窗帘/晾衣架 | 打开、关闭、暂停、开到一半 | `motor_control`、`current_position` |
| 音量/静音 | 音量 40%、最大音量、静音、取消静音 | `volume`、`mute` 或音量 action |
| 播放 | 播放、暂停、下一首、上一首 | 设备安全 action |
| 扫地机器人 | 开始清扫、暂停清扫、回充、返回充电 | `start-sweep`、`stop-sweep`、`start-charge` 安全 action |
| 门锁 | 上锁、锁门、开锁、解锁 | 锁能力或无参数 lock/unlock action；始终二次确认 |
| 批量 | 关闭所有灯、把客厅的灯全部关掉、全屋空调关闭 | 按房间/品类筛选后批量执行 |
| 排除范围 | 关闭所有灯，除了客厅灯 | `exclude_rooms`、`exclude_devices`、`exclude_categories` |
| 组合 | 打开空调并调至 24°C、关灯、关空调、开净化器 | 逐条预校验后顺序执行，任一条目标不唯一时整组不执行 |
| 查询 | 设备状态、温度、湿度、亮度、风速、电量、音量、开合度、门状态、空气质量、在线设备数量 | 对应只读属性或本地设备目录 |

相对调节会先读取当前值，再按设备 spec 的范围和步长计算目标值，写入后回读确认。只暴露不需要参数、且在白名单中的 MIoT action；门锁、摄像头隐私、重启等能力仍受高风险确认或拒绝策略约束。

“所有/全部/全屋”只会作用于当前绑定家庭或明确说出的房间/品类。批量执行会跳过离线设备，并在回复中列出失败或未执行的设备。

组合指令会先解析整组目标，再开始执行；只要其中一条出现歧义或设备不支持，整组都不会发出控制。门锁、晾衣架等需要二次确认的操作不能在组合中静默执行，必须拆成单条指令确认。

### 话术来源与覆盖原则

以下产品说明是话术矩阵的主要参考：

- [米家官网](https://home.mi.com/) 给出“打开空调并调至 24°C”这类组合控制示例。
- [小米小爱开放平台空调页](https://developers.xiaoai.mi.com/miot/aircondition) 包含打开/关闭空调、切换模式和“把空调设为 26 度”等示例。
- [小米小爱开放平台智能家居控制](https://developers.xiaoai.mi.com/miot) 说明设备接入 MIoT 后由小爱完成语义解析，设备侧负责执行。
- [小米小爱开放平台设备云对接](https://developers.xiaoai.mi.com/documents/Home?type=/api/doc/topicId/device_cloud) 给出“空调 26 度”“关闭客厅的风扇”等自然语言示例。
- [Apple 支持：用 Siri 控制配件](https://support.apple.com/guide/iphone/control-accessories-with-siri-iph2c6a1f0e/ios) 包含开灯、调亮、调温、锁门、执行场景和状态查询等常见表达。
- [Google Home：常用语音指令](https://support.google.com/googlenest/answer/7071896?hl=zh-Hans)、[Google Home：控制灯光](https://support.google.com/googlenest/answer/7071879?hl=zh-Hans) 和 [Google Home：创建日常安排](https://support.google.com/googlenest/answer/7029585?hl=zh-Hans) 用于补充批量、排除范围、场景和日常自动化表达。

这不是“所有米家设备都一定能控制”的承诺。最终能执行哪些动作，取决于设备真实 MIoT spec 中是否存在可读写属性或无参数安全 action；需要参数、厂商私有协议、门锁高级设置、摄像头隐私开关和重启等能力不会被猜测或绕过。

对无法安全判断的表达会明确拒绝而不是猜测执行，例如“不要关空调”“一小时后打开风扇”“只保留客厅灯”。定时和延时控制应使用 MiHome Mac 的“自动化”；否定和排除式表达需要改成明确动作。

## 推荐产品架构

```text
飞书 / 企业微信 / 钉钉
       |
       | 官方机器人事件、消息发送
       v
云端多租户 Gateway（共享官方机器人）
       |
       | 用户身份、设备家庭映射、限流、审计
       v
MiHome Mac 本地 Agent
       |
       | 本机设备目录、策略校验、米家 API
       v
米家设备
```

共享官方机器人需要云端多租户服务，原因如下：

- 平台只向你的机器人发送消息，不需要每个用户都创建应用。
- 云端负责平台审核、用户账号体系、订阅/额度、限流、审计与隐私政策。
- MiHome Mac 主动连接云端，不需要家庭宽带的公网 IP 或内网穿透。
- 平台凭据只存在云端，不下发给用户。
- 家庭与设备控制仍在用户本机完成，云端只转发经过签名的指令。

当前仓库实现的是“本机 Agent + 可选平台直连”。共享机器人所需的云端控制面尚未包含在仓库内，不能把当前自建应用模式包装成大众开箱即用方案。

## 如何快速引导普通用户

### 1. 把接入入口做成一个二维码

在 MiHome Mac 首页、下载页、安装完成页放同一个“添加机器人”二维码：

- 飞书：机器人名片二维码或官方机器人分享链接。
- 企业微信：机器人名片二维码或企业内应用入口。
- 二维码旁边只保留一句动作说明：“扫码添加机器人，发送配对码即可控制。”

不要让普通用户先看“创建自建应用”“配置回调”“EncodingAESKey”。这些内容只放在高级接入页。

推荐首屏文案：

```text
用手机扫码添加 MiHome 智能管家
1. 打开飞书/企业微信扫码
2. 发送桌面端显示的 6 位配对码
3. 直接说“打开客厅灯”
```

### 2. 配对码作为唯一绑定动作

用户流程控制在 3 步：

1. 安装并登录 MiHome Mac，点击“生成配对码”。
2. 扫码添加机器人，发送“配对 123456”。
3. 机器人返回“配对成功”，随后即可控制设备。

建议的机器人首次欢迎语：

```text
欢迎使用 MiHome 智能管家。
请打开 MiHome Mac → 接入中心，生成 6 位配对码后发送：
配对 123456
```

配对失败时不要只说“失败”，应附带下一步：

```text
配对失败：配对码已过期。请回到 MiHome Mac 重新生成，再发送“配对 新验证码”。
```

### 3. 首次进入机器人时自动引导

企业微信长连接已利用 `enter_chat` 事件自动发送欢迎语。飞书已处理以下官方事件，并按会话 ID 去重后发送一次欢迎语：

- `im.chat.access_event.bot_p2p_chat_entered_v1`：用户首次进入与机器人的单聊。
- `im.chat.member.bot.added_v1`：机器人被加入群聊。

欢迎语会提示生成配对码、展示控制示例，并说明桌面端必须保持运行和联网。真实租户仍需在上线前联调事件权限、客户端版本和消息发送权限。

- 未绑定用户：提示生成配对码。
- 已绑定用户：展示“打开客厅灯”“执行回家模式”两个真实示例。
- 账号离线：提示“桌面端未在线，请保持 MiHome Mac 运行并联网”。

### 4. 提供可直接复制的邀请文案

接入中心已提供“复制用户引导”按钮。运营侧还可以固定使用：

```text
【MiHome 智能管家】
电脑保持 MiHome Mac 在线，扫码添加机器人。
发送「配对 123456」绑定家庭，之后直接说：
打开客厅灯
把空调调到 26 度
执行回家模式
```

### 5. 把失败恢复做成自助流程

最常见的 4 个问题应在机器人里直接回答：

| 现象 | 机器人回复 |
|---|---|
| 没有绑定 | 回到 MiHome Mac 生成配对码，发送“配对 123456” |
| 配对码过期 | 配对码 10 分钟有效，请重新生成 |
| 桌面端离线 | 电脑睡眠、退出应用或断网时无法控制，请保持应用运行 |
| 设备歧义 | 返回候选房间/设备，要求用户补充名称 |

## 自建应用接入

### 飞书

推荐使用事件长连接，不需要公网回调：

1. 管理员在飞书开放平台创建“企业自建应用”。
2. 开启机器人能力，配置接收消息所需权限。
3. 在事件订阅中添加 `im.message.receive_v1`、`im.chat.access_event.bot_p2p_chat_entered_v1` 和 `im.chat.member.bot.added_v1`，连接方式选择长连接。
4. 记录 App ID、App Secret。
5. 发布应用，并将可用范围设置为测试成员或目标部门。
6. 在 MiHome Mac 接入中心选择“飞书 → 长连接”，填写凭据并启用。
7. 连接状态显示“已连接”后生成配对码。

Webhook 模式需要在同一事件订阅页选择请求地址模式，并把接入中心显示的完整本机回调替换成公网 HTTPS 域名后填入。不要把 `127.0.0.1` 地址直接提交给平台。

Webhook 模式仍保留给已有部署，但必须提供公网 HTTPS 隧道。当前实现会校验：

- `X-Lark-Request-Timestamp`，允许窗口为 5 分钟。
- `X-Lark-Request-Nonce`。
- `X-Lark-Signature = SHA256(timestamp + nonce + encrypt_key + raw_body)`。
- Verification Token。
- `event_id`/`message_id` 重放去重。

### 企业微信

推荐使用智能机器人 API 长连接：

1. 企业管理员进入“应用管理 → 智能机器人”。
2. 创建智能机器人并开启 API 接收消息。
3. 记录 Bot ID 与 Bot Secret。
4. 在 MiHome Mac 接入中心选择“企业微信 → 长连接”，填写凭据并启用。
5. 连接状态显示“已连接”后生成配对码。
6. 在机器人单聊或群里发送“配对 123456”。

当前协议实现包括：

- `aibot_subscribe` 认证。
- 30 秒心跳，连续心跳超时后重连。
- 指数退避，普通断线最多重试 10 次，认证失败最多 5 次。
- `disconnected_event` 表示同一机器人有新连接，旧连接停止重连，避免双方互踢。
- 流式回复透传原始 `req_id`，同一会话按顺序发送。
- 群聊使用 `chatid`，单聊使用 `from.userid` 作为会话键。

企业微信 Webhook 回调当前未接入。接入中心不允许选择该模式，避免出现“配置成功但消息不可用”的假状态。

### 钉钉

推荐使用机器人 Stream 长连接：

1. 企业管理员打开钉钉开放平台，进入“应用开发 → 企业内部应用”。
2. 创建应用并添加“机器人”能力，接收消息方式选择 Stream。
3. 在“凭证与基础信息”记录 Client ID（原 AppKey）和 Client Secret（原 AppSecret）。
4. 发布应用，并把可用范围设置为测试成员或目标部门。
5. 在 MiHome Mac 接入中心选择“钉钉 → 长连接”，填写凭据并启用。
6. 连接状态显示“已连接”后生成配对码。
7. 在机器人单聊发送“配对 123456”。

钉钉 Stream 当前使用 Robot Topic `/v1.0/im/bot/messages/get`，通过 `sessionWebhook` 回复。语音消息优先读取钉钉服务端返回的 `content.recognition`。

## 语音消息

语音链路与文字共用同一套配对、能力校验、确认和执行逻辑：

```text
平台语音 -> 平台转写或本机 ASR -> 文本 -> 意图解析 -> 本地策略 -> 米家设备
```

- 飞书：以 `type=file` 下载 `audio` 消息资源，经 ffmpeg 转成 16 kHz 单声道 WAV，再调用语音识别。
- 企业微信：读取 `voice.recognition`；没有转写时提示用户重说或改发文字。
- 钉钉：读取 `content.recognition`；没有转写时提示用户重说或改发文字。
- 每次语音执行都会先回复“我听到的是：……”，避免误识别后无感知执行。

推荐本机使用 Whisper.cpp：

1. 安装 `whisper-cli`，或在接入中心填写其绝对路径。
2. 下载 `ggml-small-q5_1.bin` 等 GGML 模型，放到 `~/Library/Application Support/MiHome/models/`。
3. 在接入中心选择“Whisper.cpp”，填写命令和模型文件路径。
4. 点击“测试语音识别”；测试会检查命令是否可执行、模型文件是否存在且大小正常。

中文识别会附带本项目的智能家居词表提示（设备、房间、打开/关闭、温度、亮度等），并把常见的繁体、同音误识别归一化为简体控制话术。短语音仍建议使用 `small` 以上模型，并尽量靠近麦克风说完整指令，例如“关闭卧室灯”。

也可以选择 OpenAI 兼容的 `/audio/transcriptions` 接口。它需要独立配置地址、模型和 API Key，不能复用仅支持文本的 WorkBuddy2API 意图模型凭据。macOS 原生语音识别保留为实验选项。

### 多模态模型与语音识别

“支持多模态”不等于“支持语音输入”。当前意图解析使用的是 OpenAI 兼容文本聊天接口，不会自动把音频内容块交给模型；即使某个聊天模型支持音频，也必须确认服务商和网关实际暴露了兼容的音频请求格式。

桌面助手更稳妥的链路是：

```text
平台语音 -> 专用 ASR -> 文本 -> 本地规则/LLM 意图解析 -> 米家执行
```

独立开发者常用的 ASR 方案按优先级为：

1. 平台事件自带转写：企业微信和钉钉已优先使用，延迟和接入成本最低。
2. 云端 ASR：OpenAI 兼容 `/audio/transcriptions`、阿里云、腾讯云、讯飞或火山引擎，适合短命令，延迟稳定。
3. 本机 Whisper.cpp：离线、隐私好，但 `whisper-cli` 每次冷启动都要重新加载模型。
4. macOS Speech：系统原生、无需模型文件，但首次授权和系统服务可用性需要单独验证。

Whisper.cpp 路径已显式使用 CPU、4 线程、beam size 1、best-of 1，避免 Intel Mac 上默认 beam search 和错误启用 GPU 带来的额外延迟；日志会分别记录下载、转码、识别、意图执行和回复耗时。进一步压缩延迟应优先使用云端 ASR，或把 Whisper 改造成常驻 `whisper-server`，而不是继续缩小模型牺牲识别率。

## 安全与隐私边界

- 模型输入不包含米家 DID、Cookie、Token 或原始设备规格 URL。
- 平台消息先做长度限制、事件去重和用户绑定校验。
- 已绑定会话有 2 秒命令冷却，避免误触、平台重试或模型调用刷量。
- 未绑定会话不能执行设备控制。
- 高风险设备操作需要用户再次回复确认码。
- 本地网关只监听回环地址，默认不暴露到局域网。
- 凭据文件使用 macOS 用户目录私有权限 `0600`，应用日志不会打印 Secret。
- 下一阶段应把平台凭据从普通 JSON 迁入 macOS Keychain，尤其是正式签名发行版。

## 当前限制

- MiHome Mac 必须保持运行。电脑睡眠、退出应用或断网时，机器人无法控制设备。
- 当前没有共享官方机器人的云端多租户服务，普通用户仍不能做到只扫码、不配置应用。
- 平台审核、隐私政策、用户协议、数据保留策略和机器人名称/头像需要在正式发布前准备。
- 飞书长连接已使用真实租户验证文本消息、状态查询、语音资源下载转写和心跳超时后的自动重连；仍使用社区 Rust SDK `lark-channel`，后续需继续观察平台事件兼容性。
- 企业微信和飞书的企业自建应用都只服务对应企业，不能直接让另一家公司的普通成员安装。
- 钉钉企业内部机器人同样只服务本企业，需要管理员创建并发布应用。
- **QQ** 只能接入 QQ 开放平台的官方机器人，不能控制个人 QQ 账号。QQ 官方机器人需要单独申请 Bot AppID、Secret、沙箱/正式发布资格，并遵守群聊 @ 与私聊消息限制；本版本不提供半成品入口，待机器人审核能力和真实账号联调后再增加。

## 上线顺序建议

1. **内部验证：** 用自建应用长连接跑通真实飞书/企业微信账号、配对、开关灯、空调和场景。
2. **小范围内测：** 发布一个共享官方机器人，10–50 个家庭，先不要开放注册。
3. **补齐云端控制面：** 用户身份、设备在线心跳、家庭映射、订阅/额度、限流、审计、删除数据。
4. **做用户引导页：** 二维码、三步说明、配对码复制、常见问题、离线提示。
5. **平台审核：** 准备隐私政策、服务条款、数据流说明、客服与滥用处理流程。
6. **公开首发：** 默认只走共享机器人，自建应用留在“高级/企业接入”。
