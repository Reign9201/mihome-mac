# 摄像头产品通道

日期：2026-10-31 · 状态：本地和远程低延迟链路均已在当前源码开发版中用真实摄像头通过

## 1. 当前状态

macOS App 的摄像头页有两条通道：

| 通道 | 实现 | 网络条件 | 现状 |
|---|---|---|---|
| 本地 | 内置 go2rtc 连接摄像头，播放器优先 MSE，其次 WebRTC，最后 HLS | Mac 与摄像头同一局域网 | 已用 069a01 验证 MSE 与 2960×1666 真画面 |
| 远程 | Rust 建立远程连接，ffmpeg 只做无转码封装，内置 go2rtc 输出 WebRTC/MSE/HLS | 跨网段，走小米转发服务 | 已用 039a01、069a01 验证 WebRTC；两路远程宫格可同时出画 |

本地通道此前把设备列表的主镜头通道 `1` 原样传给 go2rtc，go2rtc 会将其解释为第二通道并发送 `videoquality2`。摄像头认证成功但不会返回媒体包，最终表现为 15 秒读取超时。现在统一把主镜头映射为 go2rtc 的 `channel=0`，第二镜头才保留 `channel=2`；本机已从实际摄像头取到 2960×1666 JPEG 首帧。

低延迟播放实测（Safari/WebKit 独立测试页，连接本机真实摄像头 `.150`）：

| 模式 | 连接/首帧 | 分辨率 | 备注 |
|---|---|---|---|
| WebRTC | 连接 264 ms，首帧 2239 ms | 2960×1666 | 摄像头时间水印与电脑时钟差约 1–2 秒 |
| MSE | 首帧 2441 ms | 2960×1672 | 摄像头时间水印差约 1 秒 |
| HLS | 兼容回退 | 支持 HEVC | 延迟高于前两种，只在必要时使用 |

远程真实摄像头的历史验证对象是 `chuangmi.camera.039a01`，旧版 HLS 路径输出 864×480 HEVC；`chuangmi.camera.069a01` 输出 2960×1666 HEVC 20fps，云台已确认位移。旧版两路同时启动时首帧分别为 18.76 秒和 20.27 秒。新版远程链路已改为：首帧后持续通过本机 RTSP 送入内置 go2rtc，避免每秒切片带来的固定延迟。

2026-10-31 使用与产品代码相同的 FFmpeg 参数和内置 go2rtc 1.9.15 完成合成视频验证：RTSP/TCP 生产者建立成功，H.264 视频包持续到达，HLS 回退地址返回 `200`。本机 FFmpeg 4.4 也通过，兼容参数不再要求新版才支持的选项。

同日在当前源码开发版中完成真实摄像头复测：`.150` 的 069a01 和 `.186` 的 039a01 均建立 `webrtc（connected）`，远程两路宫格同时出画。单路远程从点击到播放地址就绪受 relay 发现影响，实测约 3.0 秒和 15.9 秒；另一次双路宫格中，较慢一路经历了多个 relay 候选，约 29.9 秒才完成。进入稳定播放后，截图中的摄像头时间水印与系统时间保持在约 1 秒级。随后对 069a01 连续采样 10 分 47 秒，写入 9735 个视频包，没有重连或停滞；停止时子进程和临时配置均正常回收。此前一次远程停止来自界面切换，不是播放器停滞。

远程首次连接仍需等待小米转发服务和摄像头建立会话，通常为 10–20 秒；这部分启动时间无法通过播放器消除。低延迟优化针对会话建立后的稳定播放阶段。绝对零延迟不可实现，当前目标是约 1 秒级、卡顿后自动追赶或重连。

## 2. 为什么不直接打包 micam

micam 是 Java 21 的个人实验项目，仓库没有 LICENSE，只支持单路视频，没有音频。它证明了 CS2 relay 在跨网段可用，但不能作为 MiHome Mac 的发行依赖。产品通道把 cloud 准备、PPPP relay、MISS 会话、媒体解密都放在 Rust 里；`micam` 源码没有进入构建产物。

go2rtc 是 MIT 许可，已有 `pkg/xiaomi/miss` 和 `pkg/xiaomi/miss/cs2`，但 CS2 的握手先向摄像头的局域网地址 `32108/UDP` 发发现包，再打洞；跨网段时没有可用的 relay 入口。它解决局域网，不解决远程。

## 3. 协议拆分

1. **云侧准备**：用 `userId` / `passToken` 调 `/v2/device/miss_get_vendor`，拿摄像头公钥、签名和 relay 参数；客户端生成 X25519 密钥对。
2. **PPPP relay**：向小米 relay 发 `LIST_REQ1`，拿到 relay 地址；在 `25000/UDP` 完成 `RLY_PORT`、`RLY_REQ`、`RLY_RDY`；处理 relay 重复发来的 `0x28` MISS_SETUP，回写本地地址和外部地址。
3. **MISS 会话**：在 relay 通道上发 `0x100` 明文认证 JSON，收到 `0x101` 且包含 `"result":"success"` 后用 HSalsa20 派生会话 key；后续命令用 `0x1001` 包住，正文用 ChaCha20 加密。
4. **媒体**：发 `0x102` 启动视频，收到 32 字节头 + 加密负载；解密后按 codec id 区分 H.264（4）和 H.265（5）。云台用 `0x112`，JSON 是 `{"operation":1}`：1 左、2 右、3 上、4 下。相机每次命令走一个固定步长。

## 4. Rust 模块

```text
core/src/
├── remote_crypto.rs   X25519、HSalsa20、ChaCha20
├── pppp.rs            PPPP 帧、Uid、init string、0x28 回复、媒体重组
├── relay.rs           relay 发现与 RLY_* 状态机、接收线程、命令/媒体通道
├── miss.rs            0x100 认证、0x1001 加解密、0x102 媒体、0x112 云台
├── remote.rs          云侧准备 + relay + MISS 的组合入口
├── remote_stream.rs   媒体帧 → ffmpeg 无转码封装 → 本机 RTSP → go2rtc
├── camera.rs          内置 go2rtc、局域网取流、播放地址和诊断
└── media.rs           ffmpeg 路径、端口和进程输出
```

`RemoteStream` 对上暴露 `start(session, did, quality)`、`url()`、`webrtc_url()`、`ptz(direction, speed)`、`frames()`。Tauri 只依赖这个类型，不再知道 Java 或 micam。

### 4.1 关键实现点

- **X25519 字节序**：公钥在线上是 32 字节小端，Rust 直接按字节数组传入，不转大端。
- **会话 key**：X25519 原始共享密钥再做 HSalsa20(zero nonce)，不直接当 ChaCha20 key。
- **ChaCha20**：nonce 是 4 个零字节 + 8 字节随机尾，计数器从 0 开始。
- **PPPP 帧**：32 字节头里有 channel、seq、payload 长度；DRW 负载首字节必须是 `0xD1`，帧类型才是 `0xD0`。这个字节写错会让摄像头一直不回认证。
- **低延迟中继**：ffmpeg 只把摄像头原始视频封装成 RTSP，不重新编码；内置 go2rtc 再把同一路流提供给 WebRTC、MSE 和 HLS。ffmpeg 使用到达时间生成时间戳，避免把所有型号强行当成 25fps；同步参数保持对 FFmpeg 4.4 兼容。
- **播放顺序**：本地优先 MSE，远程优先 WebRTC；当前方式不可用时按兼容性切换，限制缓冲窗口并在落后时追赶，最后才回退 HLS。
- **端口**：API、RTSP 和 WebRTC 使用三个独立的本机端口。远程推流必须使用 RTSP 端口，不能复用 API 端口。
- **进程健康**：远程启动时等待 go2rtc 收到真实 RTSP 生产者后才向界面返回播放地址；ffmpeg 提前退出时返回最近日志并清理全部子进程。
- **会话限制**：同一台摄像头同时只允许一个 P2P 会话；App 同一 did 复用已有 RemoteStream。不同摄像头可以并存，远程宫格当前用 HashMap 保存多路流；米家 App 占用同一台摄像头时，仍会提示先退出手机直播。

## 5. 验收门禁

| 项目 | 目标 | 当前 |
|---|---|---|
| 本地真画面 | 连续播放 10 分钟 | 069a01 已通过真实摄像头出画和播放器验证 |
| 本地首帧 | 首选方式 3 秒内 | Safari/WebKit 中 MSE 实测 2441 ms，另一台设备约 390–730 ms |
| 远程低延迟链路 | RTSP 生产者就绪后输出 WebRTC/MSE | 合成视频与真实摄像头均通过 |
| 远程真实摄像头 | 当前构建内出画并连续播放 10 分钟 | 两路 WebRTC 同时出画；单路连续播放 10 分 47 秒、0 重连 |
| 两路摄像头 | 两路同时出画面，不互相踢下线 | 旧版路径曾同时播放 10 分 33 秒：039a01 864×480、069a01 2960×1666 |
| 启动时间 | 尽量在 15–20 秒内；超时提供重试路径 | 常见 2.98–15.88 秒，双路宫格遇到约 29.9 秒长尾；relay 和候选状态是主要波动来源 |
| 云台 | 四个方向各按 1 秒，画面有可辨认位移；松手 300ms 内停止 | 069a01 已确认：命令前后画面从客厅左侧切到沙发/冰箱一侧，位移明显；039a01 机型不支持云台，UI 已隐藏方向盘 |
| 内存 | 单路增量 < 120MB，两路 < 220MB | 两路物理内存约 104MB（App 33MB、WebKit GPU 22MB、WebContent 38MB、两个 ffmpeg 共 11MB） |
| CPU | 单路 1080p 解码 < 15% M4 单核 | 两路采样：App 1%、WebKit GPU 2.3%、ffmpeg 0.2% 和 0.0% |
| 失败隔离 | 摄像头进程崩溃不影响设备控制、场景和登录 | go2rtc/ffmpeg 均为独立进程；崩溃场景尚未人工注入验证 |
| 合规 | 不包含 micam 代码、不依赖 JDK | 构建产物无 Java 进程；仍依赖 ffmpeg |

## 6. 后续

1. 在更多网络环境重复本地、远程 10 分钟采样，覆盖 Wi-Fi 抖动和 relay 切换。
2. 增加 ffmpeg 异常退出到界面状态的直接映射，并补自动重建测试。
3. 继续评估是否随 App 分发裁剪版 ffmpeg，减少用户额外安装步骤。
4. 如果实际设备仍无法稳定达到约 1 秒级，再评估 VideoToolbox 原生解码与显示。
